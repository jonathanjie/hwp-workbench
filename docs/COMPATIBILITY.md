# Compatibility contract — alpha 0.2.0-alpha.2

The initial engine is a preservation experiment, not a Hancom-compatible word processor certification. Always inspect its warnings before edits and independently check output before use.

## Supported boundaries

HWP support starts at 5.x, stored in a CFB version 3 or 4 container. Compressed and uncompressed paragraph streams are parsed. Contiguous existing plain text runs can be replaced with text of a different UTF-16 code-unit length, including deleting a run or filling an existing empty paragraph text run. Paragraph structure, style references and native controls are not editable. Edits cannot cross or touch native control code units. Complete paragraph headers, record counts and position metadata must pass validation. All selected segments in one batch must pass validation before anything is changed. Multiple edits in one paragraph are applied from the end backwards.

HWPX support assumes a ZIP package with `application/hwp+zip` mimetype, `Contents/header.xml`, `Contents/content.hpf` and numbered `Contents/sectionN.xml` bodies. XML must be UTF-8 and well formed, without DTDs or entity declarations. Text in namespace-qualified `hp:t` nodes can be changed, including an existing empty node and childless `fwSpace`, `nbSpace`, `tab`, `lineBreak` and `hyphen` markers. Reserved placeholders retain each marker's exact native bytes; markers can be deleted, but never invented or duplicated. Other nested elements, literal reserved-character collisions and more than 32 markers per node remain read-only. See `docs/AGENT-INTERFACE.md` for the placeholder contract. Edits do not add or remove paragraphs or text-node identities.

The format extension never substitutes for detection. Output must use the same native extension as the detected source. There is no implicit HWP/HWPX conversion, and no HTML/DOCX conversion on save.

## What preservation actually means

No-op serialization returns the original bytes. Edited HWPX output retains the uncompressed bytes of untouched members and changes text lexically within affected XML members; ZIP compression/container bytes may change. Edited HWP output retains unaffected stream payloads but rebuilds CFB allocation structures and recompresses edited sections. The writer verifies member/stream inventories, intended text values and untouched payloads with its own reader before output publication.

HWP length changes update the paragraph character count, character-shape starts, range-tag endpoints and cached line starts in UTF-16 code units. The header flag and other fields are retained. Newly collapsed character-shape starts keep the shape of surviving text or controls at the original edit end; all pre-existing duplicate starts are retained, with the surviving-content shape last at a collapsed boundary. Record headers use extended sizes when required. Untouched records keep their exact bytes.

This does not imply visual fidelity. Cached preview text and images may still describe the original content. HWP line starts are adjusted, but cached line geometry remains stale. Readers must recompute line breaks; `HWP_REFLOW_UNVERIFIED` reports that Hancom reflow has not been verified. `PREVIEW_CACHE_RETAINED` remains present. HWPX length changes can leave text-position-dependent metadata unadjusted. Equal-length replacements can also change visual width. Fonts, pagination, line breaking, object anchors and field/revision semantics are not independently qualified. The safe operating rule is a new output file followed by Hancom comparison, not blind submission.

## Protected, active and unknown content

Protected/DRM/password HWP is refused. Detected script or signature metadata blocks edits. The one exception is Hancom's default script stub (`Scripts/DefaultJScript` with an empty `OnDocument_New` and `Scripts/JScriptVersion`): when both decompressed payloads match the recorded SHA-256 hashes exactly, the document stays editable, the streams are kept byte-identical and never executed, and an `info` warning `DEFAULT_SCRIPT_STUB` is reported. Any other script content keeps the document read-only. Signed documents are not silently invalidated or stripped. The app does not execute macros, scripts, OLE or external references.

Known feature warnings cover tables, images, equations, charts, OLE, headers/footers, fields, footnotes and selected shapes. Unknown payloads are retained where possible. Detection of every unsupported feature is not implemented, so the general uncertified-layout warning is never removed. A missing feature-specific warning is not a claim of support.

rhwp draws native pages; the fallback structure preview is approximate. Table cells with editable text are not equivalent to a table editor. Existing styles may be displayed but there is no formatting toolbar because native formatting mutation is not implemented.

## Limits

Files and saved outputs: 64 MiB. One expanded part: 32 MiB. Total ZIP expansion or HWP body expansion: 128 MiB. ZIP budgets count actual inflated bytes in bounded chunks; member lengths, CRCs and deflate completion must match. ZIP members: 2,048. Text nodes: 100,000. Text operations per patch: 1,000. Text value length: 200,000 Unicode characters. Section XML depth: 128. Independent verification worker timeout: 30 seconds; desktop operations otherwise use the in-process engine. MCP input message length: approximately 4 MiB characters; this is not a full resource-isolation guarantee.

`validate` means basic container/XML/record parsing succeeded. `reopenedAndVerified` means our own reader verified the output, not that Hancom or an independent parser accepted it. No metric is reported as a percentage of Hancom compatibility.

The `apply` result reports an independent rhwp reopen and edited-text check; a failed or unavailable rhwp check does not block `apply` when the preservation engine’s own verification passes.

Explicit `save` uses the same complete patch and native self-reparse checks, keeps a private previous version, then atomically replaces the opened file without changing its format or mode. It refuses a changed disk source, read-only document, symlink path, failed independent reopen or missing edited text. Unavailable independent checks and unverified empty-text searches remain explicit in the result. The default backup folder is `<document folder>/.hwp-workbench/backups/`; ten previous versions per canonical source path are retained. New backup names include a short SHA-256 identity of that path; older names remain untouched. If a concurrent revision appears after publication, it is kept, recovery bytes are retained in this backup folder, and `SOURCE_CHANGED` names the recovery copy. `apply` and conversions never overwrite. Desktop Save uses this same engine operation; it does not establish Hancom layout fidelity.

Node `anchor` values use zero-based section and top-level paragraph indexes and Unicode character offsets from rhwp’s paragraph text API. Table-cell text keeps its containing top-level paragraph with `inCell: true` and `charOffset: null`; other nested text, such as shape text and headers, also has a null offset because this API cannot address it. The independent edited-text check first searches top-level paragraphs, then decoded `getTextFileUnicode()` output, then native nested paragraphs when export omits a nested list. Its `editMethods` field reports `paragraphs`, `fullText`, `nestedParagraphs`, `missing` or `unverified-empty` for each edited node. Empty replacements appear in `unverified`, with `editedTextsFound: false`, because substring search cannot establish that the target text was deleted. This is text-presence evidence, not a check of nested formatting or location. The corpus report lists these range checks as skipped when a file has no nonempty body text. Node rendering uses approximate text widths and does not qualify font metrics or Hancom layout.

## Explicitly not implemented

HWP text edits across controls or outside existing runs; HWP 3.x; complete native rendering or pagination; character/paragraph-format edits; paragraph insertion/deletion; table structural changes; images/stamps/object edits; native fields/form operations; new documents; comments/revisions; password/signature workflows; lossless conversion; PDF export; collaborative editing; autosaved unstaged typing; release signing and notarization.

## Explicit, lossy conversion

`convert` exports to HWP, HWPX or DOCX. It never runs as part of native save. HWPX is the pivot: HWP ⇄ HWPX uses the bundled rhwp library and its export loss report; DOCX ⇄ HWPX uses direct Rust mappers. DOC, ODT and RTF first pass through optional LibreOffice to DOCX. Format detection uses source bytes, not the filename. A same-format conversion copies the validated original bytes.

The supported mapping covers paragraphs; bold, italic, underline, strike, size, colour and one font face per run; paragraph alignment, indents and spacing; headings via styles; simple decimal and bullet numbering; tables with column widths, row/column spans, borders and solid cell shading; embedded PNG/JPEG/GIF/BMP images; section page size, orientation and margins; line breaks and page breaks. Inline DOCX page breaks split a paragraph at the break because native page breaks begin a paragraph. Paragraph text comparison uses those logical boundaries. Nonempty vertical-merge continuation cells, including image-only cells, keep their mapped content in the merge owner and report `nonemptyMergeContinuation`. Exact paragraph identity, spacing across that split, typography and pagination are unqualified.

Fields, equations, footnotes/endnotes, headers/footers, shapes, text boxes, comments and tracked changes are reported as unsupported with counts. Other encountered properties, controls and elements use named report entries. Field result text and readable revision text can survive without their original semantics; equations, drawing text and other unsupported payloads can be omitted. Complex list formats, image cropping/effects/rotation, floating placement, theme fonts/colours and unreferenced binary parts are also reported when detected. Arbitrary metadata, links, active content and signatures are not a preservation promise of conversion. The original source remains untouched. Native save still retains its existing protection and preservation rules.

**The conversion report is the contract.** Read `unsupported`, every `engineReports` entry and `textCheck`. rhwp's loss report covers its export stage; it does not measure losses that occurred while reading DOCX or constructing the pivot. An empty unsupported map and matching text do not establish matching layout or full object support. These mappers do not replace the product requirement for full native HWP/HWPX editing.

`textCheck` independently re-reads the source and output through the native engine or DOCX reader. It compares paragraph sequences after Unicode NFC and whitespace collapse within each paragraph. It reports missing, changed and added paragraphs, counts, original character totals, the comparison method and whether the sequences match. Detail lists contain at most 1000 entries, with 120-character text previews. Large comparisons use bounded multiplicity and index checks. Empty paragraphs are checked; table carrier paragraphs and empty merge continuation cells are geometry and are excluded. Unsupported object semantics and layout are outside this text check. Legacy import compares against the LibreOffice DOCX intermediate and reports `legacyImportUnverified: 1`, since the original import losses cannot be independently measured here.

Conversion is a dry run unless both `output` and `acknowledgeRisks: true` are supplied. The requested target extension is required. Output is re-read, the source hash is checked again, and the workspace's no-follow, exclusive writer publishes a new file. Existing destinations, traversal and symlink paths are refused. A missing required optional backend returns `available: false`, its reason, an incomplete route report and `textCheck.performed: false`, with no output. Backend errors and timeouts fail without publishing.

LibreOffice is not bundled. Its subprocess receives private input/output copies, a fresh temporary user profile with high macro security, `--headless`, `--norestore` and a 60-second timeout. All copies and the profile are removed on success or error. The engine does not execute document code or fetch external relationships. Conversion is not a general sandbox for an office application.

Authored conversion tests check native reopen and rhwp page-zero rendering, rich-property mapping and reports. Real LibreOffice PDF/RTF checks require `HWP_WORKBENCH_LIBREOFFICE_TESTS=1`; default suites skip them explicitly. Earlier LibreOffice qualification attempts aborted during macOS application registration. Independent PDF and real DOC/ODT/RTF qualification remain open for the orchestrator's external run. Public documents, Hancom reopen/layout, fonts and native desktop integration have not been qualified by these tests.
